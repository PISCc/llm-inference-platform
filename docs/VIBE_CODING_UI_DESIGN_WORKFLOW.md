# Vibe Coding 网页 UI 设计工作流：学习与复用手册

> 来源：视频《3招拯救 Vibecoding 丑设计！拥有大厂级 UI》
>
> 适用对象：使用 Claude、ChatGPT、Cursor、CodeX 等 AI 工具进行网页开发的产品经理、独立开发者和前端开发者。
>
> 文档目标：把视频中的方法整理成一套可以反复执行、复制到新页面和新项目中的工作流，而不是只记住几个零散 Prompt。

---

## 0. 先说结论

Vibe Coding 页面“功能能跑，但看起来很普通”，通常不是因为 AI 完全不会写 CSS，而是因为交给 AI 的设计输入不够明确：

- 没有具体的参考对象，只说“高级一点”“像大厂一点”；
- 没有把视觉参考提供给 AI，只用文字描述截图中的效果；
- 没有把已经调好的风格沉淀成规则，导致下一次迭代重新随机发挥。

视频给出的核心路径可以概括为：

> **先找对标 → 再用截图让 AI 理解 → 最后把风格固化为设计规范。**

这套方法的本质不是“让 AI 猜审美”，而是把设计工作转换成三个可操作的输入：

1. **参考样本**：我希望页面接近什么；
2. **视觉证据**：这个参考具体由哪些颜色、间距、层级和组件构成；
3. **设计规则**：之后的页面必须继续遵守什么。

## 1. 视频内容的结构化总结

视频约 9 分钟，公开章节大致分为四段：

| 时间段 | 主题 | 要解决的问题 |
|---|---|---|
| 00:00–01:05 | Vibe Coding 的审美问题 | 为什么功能完成后，页面仍然显得粗糙、普通 |
| 01:05–04:49 | 培养审美的 3 个方法 | 如何找到高质量参考，而不是闭门造车 |
| 04:49–08:47 | 精准复刻设计 | 如何用多模态 AI 分析截图并指导实现 |
| 08:47–结束 | 固化风格与总结 | 如何让设计风格在后续迭代中保持一致 |

视频公开简介中强调的三个技巧是：

1. **先有审美，找对标**：从 Awwwards、Mobbin 等参考库获取成熟设计样本；
2. **多模态“喂图”**：把实际截图交给具备视觉理解能力的 AI，让它分析配色、排版和留白；
3. **沉淀设计资产**：让 AI 生成 `design.md` 设计规范，把本次页面的风格变成后续可复用的资产。

> 说明：本手册依据视频页面公开简介和章节信息整理。下面的 Prompt、检查表和 `design.md` 模板是为了便于学习复用而做的工程化扩展，不代表视频逐字稿。

## 2. 正确理解：AI 是执行者，不是自动设计总监

### 2.1 低质量输入会产生什么结果

下面这类指令看似自然，实际上约束很弱：

```text
把这个页面做得高级一点。
配色更有质感一些。
做成大厂风格。
让它看起来更现代、更漂亮。
```

问题在于：

- “高级”没有明确视觉标准；
- “大厂风格”可能对应完全不同的产品类型；
- AI 不知道你更重视信息密度、品牌感、可读性还是视觉冲击；
- 每次重新生成都会产生不同的颜色、圆角、阴影和间距；
- 当前页面改好后，下一页又回到默认组件风格。

### 2.2 高质量输入应该包含什么

一条可执行的 UI 指令至少应包含：

```text
产品类型 + 目标用户 + 参考页面 + 必须保留的内容/功能
+ 视觉特征 + 禁止事项 + 输出要求 + 验收标准
```

例如：

```text
这是一个面向技术人员的大模型推理可视化平台。
请参考附件截图的深色技术产品风格，但不要复制其品牌标识和具体文案。
必须保留当前页面的六个模块入口、搜索、页面导航和中文术语。
重点复刻：低饱和深色背景、清晰的层级、紧凑但不拥挤的间距、克制的强调色。
禁止：渐变泛滥、玻璃拟态、夸张发光、营销落地页文案、虚构数据。
请先输出设计分析和改造计划，再修改代码。
```

## 3. 可重复执行的完整工作流

## 阶段 A：建立参考，不要直接开写

### A1. 明确页面任务

先写清楚四件事：

- 页面服务谁；
- 用户进入页面后要完成什么任务；
- 页面中哪些内容、交互和路由必须保留；
- 页面属于什么产品类型。

建议使用以下表格：

| 项目 | 示例 |
|---|---|
| 产品类型 | 正式技术产品 / 数据工具 / 教学实验室 / SaaS 控制台 |
| 目标用户 | 前端开发者、推理工程师、技术学习者 |
| 核心任务 | 阅读解释、运行模拟、比较方案、定位问题 |
| 必须保留 | 路由、模块入口、已有知识内容、计算逻辑、交互状态 |
| 设计目标 | 专业、克制、可读、信息层级明确 |
| 禁止方向 | 虚假指标、夸张营销、与产品无关的装饰 |

### A2. 选择 2–4 个参考样本

不要只找一个样本。建议为不同维度分别找参考：

- **整体气质**：页面的氛围、密度和品牌感；
- **布局结构**：导航、侧栏、卡片、表格或工作区如何组织；
- **组件细节**：按钮、标签、输入框、提示框和图表的处理；
- **响应式行为**：桌面、平板和窄屏如何收缩或重排。

参考样本不需要来自同一行业。技术产品可以参考优秀的开发者工具、设计系统、数据平台和文档产品，但要说明“借鉴哪个维度”，避免整页照抄。

### A3. 先输出设计方向

在正式改代码前，要求 AI 先给出：

1. 参考样本的共同视觉规律；
2. 当前页面的问题清单；
3. 推荐保留、调整和删除的内容；
4. 色彩、字体、间距和组件方向；
5. 改造后的页面结构；
6. 可能影响现有功能的地方。

**不要让 AI 一上来直接重写整个页面。** 先看方向是否正确，再进入实现阶段。

## 阶段 B：用截图让 AI 形成“视觉共识”

### B1. 截图准备原则

提交给 AI 的截图最好满足：

- 能看清完整页面结构；
- 同时提供桌面端和窄屏截图；
- 如果要分析组件，额外截取按钮、表格、卡片等局部；
- 不要把过多不相关的页面混在一起；
- 对每张图标注“希望借鉴什么”。

示例：

```text
图 1：借鉴整体布局和页面密度。
图 2：借鉴颜色、边框和卡片层级。
图 3：借鉴按钮、标签和输入框状态。
当前项目截图：用于对比改造前后的问题。
```

### B2. 推荐的截图分析 Prompt

```text
请分析我提供的参考 UI 截图，并把视觉设计拆解成可执行的前端规则。

请按以下结构输出：
1. 页面整体气质：产品类型、目标用户、信息密度、情绪和品牌感；
2. 布局：页面分区、容器宽度、栏宽、对齐方式和响应式变化；
3. 色彩：背景、表面、边框、主文字、次文字、强调色、状态色；
4. 字体：标题、正文、标签、数字、代码的层级和字重；
5. 间距：页面边距、区块间距、卡片内边距、控件间距；
6. 组件：按钮、输入框、卡片、表格、标签、提示、导航、弹窗；
7. 视觉效果：圆角、阴影、描边、渐变、发光、动效；
8. 可访问性风险：对比度、字号、焦点状态、颜色单独传达信息的问题；
9. 可以直接转成 design.md 的设计令牌和规则。

请区分“截图中明确观察到的内容”和“你推测的实现方式”，不要编造截图中不存在的数据或功能。
```

### B3. 让 AI 做“差异分析”，而不是只做赞美

把自己的页面截图也交给 AI，并要求输出差异矩阵：

| 维度 | 参考页面 | 当前页面 | 差距 | 优先级 | 修复动作 |
|---|---|---|---|---|---|
| 层级 | 标题、说明、操作区分明 | 所有文字权重接近 | 阅读路径不清 | P0 | 调整字号、字重、颜色 |
| 间距 | 区块有统一节奏 | 每个组件间距不同 | 页面显得杂乱 | P0 | 建立 spacing token |
| 色彩 | 背景和表面有层次 | 卡片和背景接近 | 内容不突出 | P1 | 增加 surface 层级 |
| 组件 | 状态明确 | 默认按钮样式 | 操作反馈弱 | P1 | 补充 hover/focus/disabled |
| 装饰 | 装饰服务于信息 | 阴影、渐变过多 | 视觉噪音大 | P1 | 删除非必要装饰 |

优先级建议：

- **P0：信息结构和可用性**——先修布局、层级、对齐、可读性；
- **P1：视觉系统**——再修颜色、间距、组件状态；
- **P2：个性化细节**——最后再加装饰、动效和品牌化处理。

## 阶段 C：让 AI 按规则实现，而不是自由发挥

### C1. 实现前的约束模板

```text
请根据以下设计方向改造当前页面。

【产品定位】
这是一个正式的技术产品，不是营销落地页。

【必须保留】
- 现有路由和模块入口
- 现有业务逻辑和计算结果
- 现有中文知识内容
- 已有交互状态和错误处理

【视觉方向】
- 背景：使用明确的背景层和表面层
- 层级：标题、正文、辅助信息必须有清晰差异
- 组件：所有按钮、输入框、卡片和标签使用统一规则
- 动效：只用于反馈和状态变化，不使用无意义的持续动画

【禁止事项】
- 不虚构数据、性能指标或用户评价
- 不删除已有功能来换取视觉效果
- 不引入与产品定位冲突的装饰
- 不把参考页面的品牌标识、文案和业务结构直接复制过来

【执行顺序】
1. 先检查现有代码和页面结构；
2. 输出将修改的文件和风险点；
3. 先完成布局和层级；
4. 再完成颜色和组件；
5. 最后处理动效和响应式；
6. 输出验证结果和仍需人工确认的项目。
```

### C2. 建议按“最小改动批次”迭代

每一轮只处理一个主题：

1. **布局轮**：容器、列、分区、对齐、响应式；
2. **层级轮**：字号、字重、标题、说明、数字和标签；
3. **颜色轮**：背景、表面、边框、强调色和状态色；
4. **组件轮**：按钮、输入框、卡片、表格、导航和弹窗；
5. **细节轮**：圆角、阴影、动效、图标和空状态；
6. **验收轮**：内容、交互、窄屏、键盘和构建产物。

这样做的好处是：出现问题时能知道是哪一轮引入的，不会因为“一次性重写”而失去可控性。

4. 记录响应式、键盘焦点、错误状态和减少动效行为；
5. 列出明确禁止的视觉反模式；
6. 如果无法从代码或截图确认，请标记为“待确认”，不要自行编造。

## 4. 每次新增页面时的复用流程

以后新增页面，不要重新从零描述审美，直接采用以下流程：

### Step 1：先读规范

```text
请先阅读项目根目录的 design.md。
总结本页面必须遵守的颜色、字体、间距、组件和响应式规则。
```

### Step 2：声明页面差异

```text
本页面与已有页面的差异只有：
- 页面任务：
- 新增内容：
- 新增交互：
- 必须保留的共用结构：
- 需要特别强调的状态：

其余视觉规则全部沿用 design.md，不要另起一套风格。
```

### Step 3：先做结构，再做细节

要求 AI 按以下顺序输出或修改：

1. 页面信息架构；
2. 组件清单；
3. 状态和交互；
4. 响应式策略；
5. 代码实现；
6. 截图对比和问题清单。

### Step 4：完成后更新规范

只有当新页面确实产生了可复用的新模式时，才更新 `design.md`。不要因为单个页面的临时例外就不断增加规则。

## 5. 验收清单：如何判断页面真的变好了

### 5.1 内容与结构

- [ ] 用户第一眼能看出页面的主要任务；
- [ ] 标题、说明、操作区和结果区有清晰顺序；
- [ ] 重要信息不依赖颜色单独表达；
- [ ] 没有为了“更简洁”而删除必要内容；
- [ ] 页面中的术语和文案仍然准确。

### 5.2 视觉系统

- [ ] 背景、表面和嵌入区域有层次；
- [ ] 标题、正文、辅助文字的层级明显；
- [ ] 间距遵循有限的 token，而不是每处都不同；
- [ ] 颜色数量受到控制；
- [ ] 圆角、边框和阴影保持统一；
- [ ] 强调色只用于真正需要关注的地方。

### 5.3 交互状态

- [ ] 按钮有默认、悬停、聚焦、禁用和加载状态；
- [ ] 输入框有聚焦和错误状态；
- [ ] 空状态、加载状态和错误状态可理解；
- [ ] 键盘操作有可见焦点；
- [ ] 动效不会阻塞操作，也不会制造持续的视觉噪音。

### 5.4 响应式和工程验证

- [ ] 窄屏下没有横向溢出；
- [ ] 侧栏、表格、卡片和按钮有明确的收缩规则；
- [ ] 真实内容较长时仍能正常显示；
- [ ] 交互逻辑、路由和已有计算未被破坏；
- [ ] 项目可以完成构建，并检查最终可打开的产物；
- [ ] 如果只是做视觉试验，先使用独立预览，不直接覆盖正式页面。

## 6. 常见失败模式与修复方法

### 失败 1：只使用“高级一点”类 Prompt

**问题**：AI 不知道高级的参照标准，容易增加渐变、阴影、发光和大圆角。

**修复**：提供截图，并明确要分析的维度；把“高级”改写成具体规则，例如“低饱和背景、两级表面、细边框、有限强调色、标题与正文形成明显层级”。

### 失败 2：把参考图当成整页复制对象

**问题**：参考页面的业务结构、文案和品牌语言可能不适合当前产品。

**修复**：把参考拆成“整体气质、布局、组件、响应式”四个维度，并说明只借鉴哪些维度。

### 失败 3：一次性重写整个项目

**问题**：容易破坏路由、业务逻辑、中文内容和已有交互；出现问题时难以定位。

**修复**：按布局、层级、颜色、组件、细节、验收分轮推进，每轮都检查差异。

### 失败 4：只保存代码，不保存设计规则

**问题**：新页面会重新出现默认按钮、随机颜色和不同间距。

**修复**：在视觉方向稳定后生成 `design.md`，以后每次新增页面先读取它。

### 失败 5：用装饰掩盖信息架构问题

**问题**：渐变、动效和玻璃效果不能解决内容顺序、对齐和可读性问题。

**修复**：遵循 P0 → P1 → P2 顺序，先修结构和可用性，再做视觉细节。

### 失败 6：为了“像参考图”而虚构数据或文案

**问题**：技术产品尤其容易出现假指标、假 benchmark、假客户 logo 或无法验证的性能承诺。

**修复**：视觉参考只改变表达方式，不改变事实内容；没有可靠依据时使用定性、边界清楚的表达。

## 7. 针对当前大模型推理平台的落地方式

当前项目属于**正式技术产品和大模型推理可视化平台**，因此建议这样应用视频方法：

### 7.1 参考方向

- 参考开发者工具、技术文档、数据平台和专业控制台；
- 借鉴信息层级、导航、表格、状态面板和图表的处理；
- 不把页面做成营销落地页，也不使用与技术内容无关的装饰；
- 保留 M1–M6 的模块边界、中文知识内容和现有交互契约。

### 7.2 设计改造顺序

1. 先做一个独立的视觉预览，确认方向；
2. 对比当前页面和参考页面的布局、层级、颜色及组件差异；
3. 只在确认后的方向上修改正式源代码；
4. 生成或更新项目级 `design.md`；
5. 逐个检查 M1–M6 的共用组件和跨页面一致性；
6. 运行构建并检查最终可打开的产物。

### 7.3 对技术内容的额外约束

- 技术解释要优先于装饰；
- 公式、Token、KV Cache、候选原因和证据链需要保持准确；
- 不把演示过程数据包装成生产性能 benchmark；
- 诊断页面要保留候选原因和验证路径，不能只给出没有证据的“根因”；
- AI 生成的视觉改造不能改变页面的数据结构和内容契约。

## 8. 最小可执行版本：30 分钟练习

如果只想快速练习一次，可以按下面的缩短版完成：

### 第 1–5 分钟：选参考

选 2 张截图：一张参考整体布局，一张参考组件细节。分别写明想借鉴什么。

### 第 6–10 分钟：让 AI 分析

使用截图分析 Prompt，让 AI 输出色彩、字体、间距、组件和布局规则。

### 第 11–20 分钟：只改一个页面

先让 AI 修改布局和层级，不要同时改动所有页面、路由和业务逻辑。

### 第 21–25 分钟：做差异检查

分别检查：标题层级、卡片间距、颜色层次、按钮状态、窄屏布局。

### 第 26–30 分钟：生成规范

让 AI 根据已确认的代码和截图生成 `design.md`，并人工删除不准确或只适用于单个页面的规则。

## 10. 一页纸记忆卡

> **找对标**：先看优秀案例，建立具体的审美参照。
>
> **喂截图**：让 AI 看见真实的配色、层级、排版和留白。
>
> **写规范**：把一次调好的页面变成 `design.md`，让后续页面继续保持一致。
>
> **分阶段**：布局先于颜色，层级先于装饰，验收先于发布。
>
> **守边界**：视觉改造不等于删除功能、篡改内容或编造数据。

这套方法真正要复用的不是某个网站的颜色，而是**把审美转化为参考、规则、约束和验证步骤的能力**。
